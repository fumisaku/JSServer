GMフリーズ問題 修正レポート

対象システム: JS Server (GM アプリケーション)　／　調査・修正日: 2026年7月

1. 問題の概要

GMで全ジャッジのSEND済みを検知した後、画面がフリーズする事象が発生した。 F501（採点集計画面）が更新されず、関連端末への電文送信も行われない状態が続き、 操作不能になることがあった。

調査の結果、フリーズの原因は1つではなく 複数のデッドロック構造 が重なっていたことが判明した。 今回の対応で確認・修正したものをすべて以下に記録する。

2. SEND_RESULT受信後の処理フロー（正常時）

3. 発見した原因と修正内容

原因① Stopタイマー・更新タイマーStart での二重 Invoke デッドロック

原因： 非同期スレッドから Stopタイマー() / 更新タイマーStart() を呼ぶと、 これらのメソッドが内部で Me.Invoke() を呼んでいた。 さらにその呼び出し元自身がすでに Me.Invoke() の中にいる場合、 UIスレッドが自分自身の完了を待つ「二重 Invoke デッドロック」が発生した。

修正： InvokeRequired チェックを追加し、UIスレッド上からの呼び出し時は Invoke を経由せず直接メソッドを呼ぶように変更。 また Thread.Sleep を削除してUIスレッドの占有をなくした。

ファイル修正内容コミット
F_GM.vb Stopタイマー() / 更新タイマーStart() / 更新タイマーStop() に InvokeRequired 分岐追加、Thread.Sleep 削除 d40fd2c, 3ef7065

原因② F501_更新実行() での二重 Invoke デッドロック

原因： RaiseEvent 全ジャッジ送信済みイベント → Form1 → F200.F501_更新実行() の呼び出し経路は すべてUIスレッド上で同期実行される。しかし F501_更新実行() が 無条件に Me.Invoke() を呼んでいたため二重 Invoke デッドロックが発生した。

修正： InvokeRequired チェックを追加し、UIスレッド上からの呼び出しでは 直接 F501_更新() を呼ぶよう変更。

ファイル修正内容コミット
画面\F200_採点進行確認.vb F501_更新実行() に InvokeRequired 分岐追加 b4be7ce

原因③ SEND_JK系のTCP送信がUIスレッドをブロック

原因： 全SEND確定後に関連端末へのTCP送信（SEND_JK_MU_Progress 等）を UIスレッド上で直接実行していた。接続数 × ネットワーク遅延の分だけUIスレッドが 占有され、その間に届く電文の Me.Invoke が積み上がった。

修正： 関連端末への送信処理を Task.Run で別スレッドに移動。 関連Client_list のスナップショットをUIスレッド上で取得してから Task.Run に渡す方式とし、競合アクセスも防止。

ファイル修正内容コミット
F_GM.vb 関連端末送信を Task.Run で非同期化、スナップショット方式に変更 1833f97, a12cbfe
TCPClient.vb Send() にタイムアウト5秒・1回リトライ・エラーログ追加 54b0896
LOG_C.vb LogAdd() に SyncLock を追加しファイル競合を解消 1833f97

原因④ F501内の Me.Invoke(LogDelegate) による二重 Invoke デッドロック（1回目フリーズ）

原因： F501_得点詳細_C.vb の 更新() / 更新_V2() 内で、 ログ出力のために Me.Invoke(LogDelegate, ...) を InvokeRequired チェックなしで無条件に呼んでいた。 これらのメソッドはUIスレッド上から呼ばれるため、二重 Invoke でデッドロックが発生した。

発生条件： ログレベル4が有効（LOGLEVEL >= 4）かつ F501が開いていて PCS数 > 0 のとき。デバッグログが有効な環境でのみ発生するため、 気づきにくい問題だった。

修正： 8箇所すべての Me.Invoke(LogDelegate, ...) に InvokeRequired チェックを追加。UIスレッド上からの呼び出しでは 直接 WriteLog() を呼ぶよう変更。

ファイル対象箇所コミット
画面\F501_得点詳細_C.vb 更新()、更新_V2()、Timer1_Tick、Timer2_Tick、PB_更新_Click、PB_Cali設定_Click×2、TabVisibleChange の計8箇所 c356919

原因⑤ Me.Invoke のブロッキングによる TCP 受信スレッド詰まり（2回目フリーズ・根本原因）

原因： 複数のジャッジが同時に SEND した場合、各ジャッジの SEND 電文は 別々の TCP 受信スレッドで受信される。 Me.Invoke（同期）はUIスレッドの処理が完了するまで 呼び出しスレッドをブロックする。

TCP受信スレッドAが Me.Invoke でUIスレッドを占有し、 F501.更新()（ファイルI/O含む重い処理）を実行している最中に、 TCP受信スレッドBが Me.Invoke を呼ぶと、 スレッドBがUIスレッドの空きを待ってブロックし続ける。 TCPスタックが詰まり、以降の通信が処理されなくなる。

さらに SyncLock lockObj を Me.Invoke の中で使っていたが、 UIスレッドは1スレッドのみであるため SyncLock は無意味であり、 かつデッドロックの原因となり得る余計な構造だった。

修正： Me.Invoke を Me.BeginInvoke（非同期・即リターン）に変更し、 SyncLock lockObj を削除。 TCP受信スレッドはUIキューに処理を投入した後即座にリターンするため、 次の電文の受信がブロックされなくなった。 UIスレッドはキューに積まれた処理を順番に実行し、 全SEND処理済FLAG により全SEND後処理の二重実行も引き続き防止される。

変更前の構造（デッドロック発生）
【TCP受信スレッドA (R のSEND)】 Me.Invoke(Sub() ← UIスレッドを占有して完了を待つ（ブロッキング） SyncLock lockObj J_Send色付け() → F501.更新() ← ファイルI/O + 集計（重い） End SyncLock End Sub) ← スレッドAはここで200ms以上ブロック 【TCP受信スレッドB (H のSEND・ほぼ同時）】 Me.Invoke(Sub() ← UIスレッドはスレッドAの処理中 → 永遠に待機 → フリーズ
変更後の構造（正常動作）
【TCP受信スレッドA (R のSEND)】 Me.BeginInvoke(Sub() ...) ← UIキューに投入して即リターン ← すぐ次の電文を受信可能 【TCP受信スレッドB (H のSEND)】 Me.BeginInvoke(Sub() ...) ← UIキューに投入して即リターン ← すぐ次の電文を受信可能 【UIスレッド】 キューから処理Aを取り出して実行 → 全SEND後処理 → F501.更新() キューから処理Bを取り出して実行 → 全SEND処理済FLAG=True → スキップ

5. 教訓・設計上の注意点

パターン問題正しい対処
UIスレッド上から Me.Invoke() を呼ぶ 二重 Invoke でデッドロック InvokeRequired を確認してから Invoke する
TCP受信スレッドから Me.Invoke()（同期）を呼ぶ UIスレッドの重い処理中に後続スレッドが積み上がりフリーズ Me.BeginInvoke()（非同期）で即リターンする
UIスレッド上で SyncLock を使う UIスレッドは1スレッドなので無意味。かつデッドロックの温床になる UIスレッド上では SyncLock 不要。削除する
UIスレッド上でTCP送信・ファイルI/Oを直接行う ネットワーク遅延・ファイルアクセス時間の分だけUIがブロックされる Task.Run で別スレッドに移動する
複数スレッドからログファイルに同時書き込み ファイル競合でブロック・例外発生 LogAdd() を SyncLock で排他制御する
